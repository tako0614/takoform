# v1からの移行

このページは、Takoform v1を利用している作者・実装者が、v2を採用するときに確認する事項を
まとめた非規範の解説です。v2を初めて使う場合は、[概要](README.md)から読み始めてください。
v1の仕様を変更したり、既存資源を自動変換する手順を定義したりするものではありません。

## 何が変わるか

v2では、作者がHTTPSで公開した版固定の仕様URLをFormの識別子として使います。
Hostはその仕様を実装し、対応状況を返します。Formの存在をHostが認定する仕組みではありません。

| 項目 | v1を使うときの前提 | v2の構成 |
| --- | --- | --- |
| Formの識別 | FormRefと機械可読な定義を使う | 作者が公開する版固定のHTTPS仕様URLを使う |
| 仕様の提供 | Form Packageと検証・信頼の契約を使う | 人間が読める仕様を公開する。機械可読な補助物は任意 |
| Hostの対応 | v1の提供・対応確認の契約に従う | 正確なForm URLへの対応を`support`で確認する |
| 資源の変更 | v1の準備・実行の契約に従う | 作成・更新・削除を直接要求する。previewは任意 |
| 操作の結果 | v1の状態・操作の形式に従う | ResourceとOperationの共通形式を使う |
| ライブラリ・Provider | v1向け実装の対応範囲に従う | 各ソフトウェアが対応するAPIとFormを明示する |

これは移行時の見取り図です。正確なv1の要求・応答は[v1仕様](../v1.md)、
v2の要求・応答は[HTTP API](http.md)を参照してください。

v2だけを実装するHost、クライアント、ライブラリは、v1のpackage、署名、Snapshot、
`schemaDigest`、準備手順、旧データ形式を持たずにv2へ適合できます。
v2の採用に合わせてv1へ機能を追加する必要もありません。
署名などを独自の供給網対策として使うことはできますが、v2共通の必須条件ではありません。

## v1の文書と利用を残す

公開済みv1の仕様、schema、参照URL、tag、releaseは、従来の内容を保持します。
保存対象は[v1の凍結記録](../v1.freeze.json)で確認できます。
v1の本文をv2の説明へ上書きしたり、v1のURLをv2へ転送したりはしません。

Takoformの新しい仕様設計・案内・新規採用はv2を中心にします。
第三者がv1を利用・実装し続けることを禁止する方針ではありません。
各Hostのv1対応期間、ライブラリの保守期間、旧資源の保持方針は、それぞれの製品が案内します。
API仕様が残っていることと、あるサービスがそのAPIを提供し続けることは別です。

## Form作者が確認すること

既存の機械可読な定義をURLへ置くだけではなく、利用者とHost実装者が読める仕様を用意します。

1. 版固定のURLと、資源の意味が分かる名前を選びます。
2. 入力・秘密入力・観測状態・出力を説明し、省略時や更新時の意味を記載します。
3. 作成・取得・更新・削除の成功条件と、部分失敗の復旧・後始末を定義します。
4. 参照先との関係、所有範囲、InterfaceやBindingの条件を記載します。
5. 例を使って、別の実装者が同じ意味に実装できるかを確認します。

具体的な完成例と要件は[Formの定義](forms.md)にあります。
v1の定義や配布物を参考資料として残すことはできますが、それだけでv2のURLと同じ仕様だと
推定してはいけません。どの仕様を実装するかは、正確なURLで指定します。

## Host・クライアント・Providerが確認すること

まず、v2用の要求・応答と、対応するFormを実装します。
既存の実行バックエンドを共有するか、v2を別実装にするかは製品が選べます。
共通バックエンドやv1/v2変換層を持つこと自体は、v2への適合条件ではありません。

同じ資源を複数APIから扱う場合は、APIをまたいでUIDごとの世代と実行の排他制御を維持します。
一方、再送キーはAPI版ごとに別の範囲に属します。
v1の要求をv2のキーで再送すれば同じ操作になる、という互換性は定義していません。
失われた応答の照合は、元のAPIと元の操作の契約に従って行います。

ProviderやSDKでは、対応するAPI版とForm URLを利用者が確認できるようにします。
ソフトウェアの更新を、既存stateや資源の自動移行と同一視しないでください。
既存資源を引き継ぐ機能を提供する場合は、その製品が変換できる範囲と失敗時の扱いを示します。

## 既存資源を引き継ぐ前の確認

v2の通常更新は、ResourceのForm URLや実行先を変更する操作ではありません。
APIの切替だけで旧資源が引き継がれることも、新しいFormへ変換されることも保証しません。

製品固有の移行方法を選ぶときは、少なくとも次を確認すると、作り直しや二重管理を避けやすくなります。

- 元の資源と新しい管理記録の対応を、どの識別子で確認するか。
- 受理済み・実行中・結果不明の操作を、どちらのAPIで照合するか。
- データ、秘密値、参照関係、接続先を、どこまで保持できるか。
- 古い実装と新しい実装が、同じ資源へ同時に変更を送らないか。
- 途中で止まった場合に再開できるか、戻す場合にどの状態へ戻せるか。
- 移行後に状態取得・更新・削除まで行えるか。

この一覧は移行設計の確認用であり、すべてのHostに共通の移行機能を要求するものではありません。
新規利用者は旧資源の移行を経ずにv2を利用できます。
