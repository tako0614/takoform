# Formの意味を定義する

この文書はTakoform v2のForm識別子、版、仕様に記す内容を定めます。Form作者は資源の意味を定義し、Hostはその仕様を実装します。要求と応答の共通形式は[HTTP API](/en/spec/host-api/v2/http)が定めます。

## 記述例: KeyValueEntry

次は、Hostが管理するkey/value集合に名前付きの文字列を一つ置くFormの架空の記述例です。URLには予約された `example` ドメインを使っています。このFormは公開済み製品でも、推奨仕様でもありません。

| 項目 | 値 |
| --- | --- |
| Form URL | `https://forms.publisher.example/key-value-entry/1.0.0` |
| Host API | Takoform Host API v2 |
| 目的 | Hostが管理するkey/value集合に、名前付きの文字列値を一つ表します。 |

### 入力

公開する `spec` オブジェクトは次のフィールドだけを持ちます。

| フィールド | 要件と意味 | 作成後の変更 |
| --- | --- | --- |
| `key` | 必須の文字列。Unicodeスカラー値で1〜128文字。同じHost、同じSpace、同じForm URLの資源内で一意です。既定値はありません。 | 変更できません。変更する場合は別のentryを作成し、旧entryを削除します。 |
| `value` | 必須の文字列。Unicodeスカラー値で0〜4096文字です。空文字列も有効です。既定値はありません。 | 変更できます。更新では保存値を置き換えます。 |

このFormに秘密入力はありません。`spec` の未知のフィールドは拒否します。長さはUTF-8のバイト数ではなく、Unicodeスカラー値の数で数えます。Hostは条件に合わない入力を、entryを変更する前に拒否します。

### 観測状態と出力

登録済みResourceを取得するとき、背後のentryが見つからなくても、Host API共通形式のResourceを返します。まだ一度も観測していない場合は `observed: {}`、`observedAt: null` です。観測済みの場合は `entryExists`（真偽値）を含め、entryが存在する場合にだけ `key` と `value` も含めます。確認できない状態を `entryExists: false` としてはいけません。観測値はResourceの `observedAt` 時点のものです。このFormはGETごとの外部再照会や、追加の鮮度保証を要求しません。登録されていないResourceの取得結果は、共通Host APIの規則に従います。

このFormの `output` は空のオブジェクトです。作成または更新の成功は、Hostが要求値を受け付けて保存したことを意味します。外部システムへの複製や、アプリケーションの稼働までは保証しません。

### 操作、失敗、削除

- **作成:** entryを一つ追加します。同じHost、同じSpace、同じForm URLに同じ `key` のentryがあれば、既存entryを変更せず失敗します。別Hostや別Form URLの同名 `key` とは衝突しません。
- **取得:** 登録済みResourceと、最後に確認できたentryの状態を返します。存在・不在・未観測を上記の形で区別します。entryが外部要因で消えても、管理記録がある間はResourceを返します。
- **更新:** `value` だけを変更できます。`key` の変更要求は副作用なしで拒否します。entryが見つからない場合、更新によって再作成しません。
- **削除:** このResourceが表すentryを削除します。entryがすでにないと確認できた場合も削除完了です。別Resourceや集合は削除しません。作成に失敗して `error` になったResourceも、この削除で残ったentryと管理記録を後始末できます。

このFormではHostがentryを所有します。他Resourceへの参照、Interface、Bindingはありません。削除の影響は対象entryだけです。

この例はAPIの共通本文形式、operation ID、世代、HTTP status、再送キーの形式や扱いを定義しません。それらは共通Host API仕様に従います。機械可読なschemaを使わない実装も、このFormを名乗るなら、ここに記した意味と入力条件を検証する必要があります。

## Form作者が公開する仕様

Formは、ある種類の資源について、その版での意味を定める仕様です。作者が管理する絶対HTTPS URLで、人が読める規範仕様を公開します。HostとクライアントはそのURLの文字列そのものをFormの識別子として使います。URLは仕様を識別するものであり、コードやpackageの取得指示ではありません。

仕様はMarkdownやHTMLなど、人が読める形式で構いません。独立したHost実装どうしが互換な入力検証と結果を実現できるよう、挙動を具体的に記します。JSON Schema、例、表などの機械可読な資料を添えても構いませんが、必須ではありません。補助資料と規範文が食い違う場合は規範文を優先し、補助資料を修正します。補助資料の有無にかかわらず、Hostは規範文に従って実装し、入力を検証します。

Hostが対応するのは、自ら明示的に実装したFormです。資源要求に含まれるURLを取得してFormを発見したり、そのURLからコードを実行したり、補助資料を自動取得したりしません。仕様を公開しただけでは、どのHostの対応も成立しません。

## Form URLの識別子と版

Form URLはASCII文字だけで直列化した絶対HTTPS URLとし、ホスト名とパスを含めます。ユーザー情報、クエリ、フラグメントは含めません。URLに非ASCII文字が必要な場合は、必要に応じてUTF-8のパーセントエンコードを使います。比較は直列化後の文字列の完全一致です。大文字・小文字の変更、パスの正規化、転送、別名、見た目が似たURLを同一の識別子とみなしてはいけません。Hostは転送を追跡したり、別URLに置き換えたりしてFormの識別子を確定してはいけません。

あるURLで公開した仕様の意味は変えません。契約を変更するときは新しいURLで公開し、旧URLの意味を黙って変更しません。`/key-value-entry/1.0.0` のようなSemVer形式のパスは作者にとって便利な慣習ですが、Takoformが要求する版系列ではなく、互換性を推定する規則でもありません。

- `latest` やbranch名など、後から指す内容が変わるURLは資源要求の識別子に適しません。
- パスにSemVerがあっても、互換性を自動推定できるわけではありません。挙動を仕様に記し、新しい識別子が必要かは作者が判断します。
- Formの識別子と互換性は、Host APIの版、SDK・クライアント・各Providerのソフトウェア版とは別です。ソフトウェアだけを更新してもForm URLは変わりません。
- InterfaceやBindingごとに独立したpackageや版系列を持つ必要はありません。必要な契約はForm仕様の章に記すか、版が固定された外部契約を正確な識別子で参照できます。

公開者がドメインを変更しても、旧URLはそのFormの識別子のままです。同じ挙動を新しいURLで公開しても、それは別の識別子です。転送によって旧URLの識別子を移転したり、別名にしたりはできません。Hostとクライアントは既存ResourceのForm URLを自動で付け替えません。移行する場合は、該当するHostとクライアントの仕様に従って明示的に行います。

## 仕様に記す8項目

章の順序や書式は自由で、固定のひな型や機械schemaは要求しません。秘密入力やBindingなどがない場合も、その項目を「なし」と明記します。

1. **目的と範囲。** 資源の種類と表す対象、使用するHost APIの版を記します。Formが実際には所有しない基盤やアプリケーションの挙動まで管理するかのように書きません。
2. **入力と既定値。** 公開入力ごとに意味、型、必須かどうか、省略時の扱い、既定値、受理範囲や上限を説明します。Formが定める既定値とHost実装上の既定値を区別します。作成後に変更できる項目、置換や明示的な移行が必要な項目も記します。
3. **秘密入力。** 秘密値を公開するdesired inputと分けて列挙し、用途、必須かどうか、必要な秘密入力を利用できない場合の挙動を説明します。秘密値そのものを公開例、schema、observed、output、通常のログに含めません。
4. **観測状態、出力、利用可能状態。** 各観測値の意味と、未取得・古い値になり得る条件、各outputの意味を説明します。利用可能状態を示す場合は、観測できる成立条件を定義します。Formが条件を定義・測定していないのに、Resourceの管理操作成功をアプリや接続先の稼働保証と同一視しません。
5. **操作と失敗。** 対応するcreate、read、update、deleteの挙動、前提、検証、意味のある失敗条件を説明します。結果が不明なときに再試行して安全かどうかも記します。操作が定義されていても、入力、認可、依存関係、実行環境に問題があれば成功するとは限りません。
6. **参照、所有、削除。** 他Resourceへの参照、その所有者、参照が固定されるか再解決されるか、削除による影響を説明します。削除が対象Resourceだけに及ぶのか、関連Resourceやデータにも及ぶのかを明記します。
7. **InterfaceとBinding（該当する場合）。** Formが必要とする、または提供する接続・操作の意味を説明します。可能ならForm仕様内に記し、外部契約を参照する場合は安定した正確な識別子を使います。参照だけでHostに権限が付与されたり、認証情報が提供されたりするかのように記しません。
8. **未知のフィールドと拡張。** 入力オブジェクトに未知のフィールドがある場合の扱い（拒否、無視、保持、その他の規則）をFormごとに明記します。未知のフィールドに暗黙の共通方針はありません。対象オブジェクトの各境界で一貫した規則を定め、既存入力の意味を保ちながら将来拡張する方法も説明します。

Formが特定の実装や環境に依存するなら、その依存条件や制限をFormの契約として明示し、他の環境にも適用できるという含意を避けます。外部標準に挙動を委ねる場合は、対象標準の正確な識別子と、委ねる範囲を記します。
