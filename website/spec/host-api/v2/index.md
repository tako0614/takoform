# Takoform Host API v2

Takoformは、サーバーやストレージなどの資源を、提供するHostが違っても共通のHTTP APIで
作成・取得・更新・削除するための仕様です。資源ごとの入力や動作は、作者がHTTPSで公開する
**Form**という仕様で定義します。Hostは対応するFormを実装し、クライアントはその仕様に従って操作します。

## この仕様の読み方

最初にこのページで基本概念を確認し、目的に合うページへ進んでください。

| 目的 | 読む順序 |
| --- | --- |
| APIを使って資源を操作する | [具体例](/spec/host-api/v2/examples) → [HTTP API](/spec/host-api/v2/http)の必要な操作 |
| 自分の資源の仕様を公開する | [Formの定義](/spec/host-api/v2/forms)の完成例 → 記述要件 |
| Hostやクライアントを実装する | この概要 → [HTTP API](/spec/host-api/v2/http) → 対応するFormの仕様 |
| v1の実装・資源を引き継ぐ | [Migration](/spec/host-api/v2/migration) → v2の各仕様 |

この概要、[HTTP API](/spec/host-api/v2/http)、[Formの定義](/spec/host-api/v2/forms)がv2の規範文書です。
規範文書は、実装が満たす条件を定めます。[具体例](/spec/host-api/v2/examples)と[Migration](/spec/host-api/v2/migration)は
理解を助ける非規範の解説であり、新しい適合条件を加えません。

## 1. 基本概念

### Form：資源の仕様

Formは「どのような資源を、どの入力で、どう操作できるか」を定めます。
入力、観測できる状態、出力、更新可能な値、削除の範囲などを、人間が読める文書に記述します。
Host APIは共通の通信方法を、Formは資源固有の意味を担当します。

各Formは、作者が所有する版固定の絶対HTTPS URLで識別します。
たとえば `https://forms.publisher.example/key-value-entry/1.0.0` という形です。
このURLは説明用で、実在するFormの公開を示すものではありません。

同じURLは常に同じ仕様を表します。資源の意味を変えるときは、新しい版のURLを公開します。
HostとクライアントはURLの完全な文字列一致でFormを識別し、名前の類似や転送先から同一性を推定しません。
URLの文法は[HTTP APIの共通形式](/spec/host-api/v2/http#common-format)に定めます。

### Host：仕様を実装して資源を提供するサーバー

HostはFormを実装し、実際の作成・保存・実行を行います。利用者の認可、提供条件、
実行先の選択、途中失敗からの復旧もHostが担当します。

クライアントはHostの対応確認APIで、必要なFormが実装されているかを調べます。
Formが作者のサイトに存在することと、HostがそのFormに対応していることは別です。
対応済みであっても、利用権限や空き容量、料金の同意、個々の実行成功を保証するものではありません。

Hostは、明示的に実装したFormだけを操作します。要求のForm URLを使って任意の外部サイトを
自動取得したり、コードを実行したりしません。作者のサイトが停止していても、既存資源の
取得・更新・削除・復旧を続けられる必要があります。

### Resource：管理する一つの資源

ResourceはHostが管理する資源の記録です。次の三つを分けて持ちます。

| フィールド | 意味 |
| --- | --- |
| `spec` | 利用者が指定した、資源をどう構成したいかという入力 |
| `observed` | Hostが実行先で確認した状態 |
| `output` | 接続先など、資源を利用するために返す値 |

それぞれの内容はFormが定めます。作成要求を受け付けた時点では、実行先に資源が存在するとは
限りません。更新中には`spec`と観測済みの状態が異なることもあります。

HostはResourceごとにUIDを発行します。UIDは削除後も再利用しないため、同じ名前で
作り直した資源に、古い資源向けの要求が適用されることはありません。
資源の管理区画を**Space**と呼び、同じSpace内の名前はFormをまたいで一意です。
単一所有者のHostは一つのSpaceだけでも構成できます。

`generation`は、作成・更新・削除の受理によって進む世代です。
`observedGeneration`と`observedAt`は、どの世代をいつ確認できたかを示します。
両者を分けることで、要求が受理されたことと、実行先で反映を確認したことを区別できます。
通常の更新ではForm URL、Space、名前、選択済みのOfferingは変更しません。

### Operation：受理した操作とその結果

作成・更新・削除を受理したHostは、実行の速さにかかわらず**Operation**を返します。
Operationには、対象のResource UID、世代、操作の種類、進行状態、実行先への効果を記録します。
クライアントはOperationを取得して完了を確認します。

```text
作成要求 → Operationを受理 → Hostが実行 → Operationの結果を取得
                                           ↓
                               Resourceの状態・出力を取得
```

管理操作の成功は、アプリや外部通信先が利用可能であることとは別です。
たとえば資源の作成後に接続先の起動を待つ必要があるなら、その判定方法をFormが定めます。
Resourceの`phase:idle`だけで、アプリが利用可能と判断してはいけません。

## 2. 操作の流れ

1. Hostの接続情報を取得し、APIの接続先と認証方法を確認します。
2. 利用する正確なForm URLを指定し、Hostの対応状況を確認します。
3. Offeringを使うHostでは、提供条件を確認して選択します。
4. Formに従う入力を指定して資源を作成し、返されたOperationで完了を確認します。
5. Resourceの状態・出力を使います。更新・削除には現在の世代を指定します。

**Offering**は、Hostが提示する実行先・制限・提供条件の選択肢です。
Offeringを使うかどうかはHostが接続情報で宣言します。使う場合は作成時に明示的に選択し、
使わない場合は入力から省きます。Offeringがないことは、無料であることを意味しません。

API識別子は`forms.takoform.com/v2`です。接続情報の経路は
`/.well-known/takoform/v2`、標準のAPIルートは`/apis/forms.takoform.com/v2`です。
すべての経路と要求・応答は[HTTP API](/spec/host-api/v2/http#endpoints)にまとめています。

直接の作成・更新・削除が標準の操作方法です。Hostは任意で副作用のない事前確認
（preview）を提供できますが、その結果を実操作の必須条件にはしません。
実操作では、その時点の入力、認可、依存関係、供給条件、競合を検査します。

## 3. 競合・再試行・途中失敗

更新・削除には現在の`generation`を指定します。他の操作が先に受理されて世代が変わって
いれば、Hostは競合を返します。知らない変更を上書きすることを防ぐための条件です。

作成・更新・削除には、操作ごとに選んだ`Idempotency-Key`を付けます。
応答を受け取れず再送するときは、元のキーと元の要求内容をそのまま使います。
Hostは定められた保持期間内なら元のOperationを返し、別の資源や操作を作りません。
保持期間を過ぎた要求の扱いは[再試行と保持](/spec/host-api/v2/http#retry)に定めます。

Hostは再起動しても、受理した操作と実行先の資源の対応を維持します。
送信前、結果確定済み、送信した可能性があり結果不明、を区別し、
結果が分からない操作を別名や別IDで作り直しません。時間切れや単発の404だけで、
実行先に変更がなかったと判断してはいけません。

途中まで変更して失敗した場合も、Hostは残った資源との対応を保持します。
Formは、同じResourceの更新または削除による復旧・後始末を定義します。
結果の照合も安全な再送もできない間は、不確実な状態を利用者に示します。

## 4. 秘密入力

Formは、パスワードなどの秘密値を`privateInputs`として定義できます。
これは操作で資源へ設定する値であり、Hostへ接続するための認証情報とは別です。
HostとFormの両方が対応する場合だけ利用できます。

秘密値は通常の`spec`、Resource、Operation、観測状態、出力、ログへ返しません。
クライアントも通常の公開構成や公開stateへ複製せず、秘密を扱う入力経路を用意します。
Hostは再試行用の記録へ平文を保存せず、照合用の単純なハッシュも公開しません。

非同期実行や再起動に備えるため、Host内部で期限付きの暗号化保存を行うことはできます。
実行先へ設定済みの秘密値と、Hostが転送のために一時保存する値は別です。
具体的な暗号方式、保存先、保持時間、上限、鍵管理、バックアップはHostが決めます。

一時値を失った場合、未送信と確認できる工程は同じOperationで再入力を待てます。
元と同じ値を補給して継続し、値を変える要求は新しい更新として扱います。
照合できない値や実行結果の不確実性を、再入力だけで解消したことにはしません。
正確な条件は[秘密入力](/spec/host-api/v2/http#private-inputs)に定めます。

## 5. 仕様と実装の分担

| 所有者 | 定義すること |
| --- | --- |
| Takoform API | HTTP形式、ResourceとOperation、競合・再試行、エラー、秘密入力の扱い |
| Form作者 | 資源固有の入力・状態・出力、操作の意味、依存関係、接続条件 |
| Host | 対応Formの実装、認可、実行先、供給制限、状態の保存と復旧 |
| クライアント | FormとHostの選択、入力の作成、結果の利用 |
| ライブラリ・Provider作者 | 自分が対応する仕様への変換と、ソフトウェアの互換性 |

Formには、人間が読める規範仕様が必要です。JSON Schemaやコード生成用データは任意の
補助物であり、対象の仕様URLを示します。文章との矛盾を暗黙に上書きするものではありません。
共通の制約言語や、すべての資源を分類する共通の種類一覧は要求しません。

資源の通信方法を表す**Interface**、資源同士の接続条件を表す**Binding**は、
Form内の章として定義できます。必要なら版固定の外部仕様も参照できます。
アプリのコード、イメージ、データの転送方法も、それを必要とするFormが定めます。
すべてのHostが共通のアップロード機能を持つ必要はありません。

Formの提供方法はHTTPSでの仕様公開です。packageの配布や署名、透明性ログ、
失効履歴の取り込み、Snapshotの生成は、APIへの参加条件ではありません。
Hostの実装者は作者と実装する仕様を確認します。URLだけで過去の文書の内容や供給元の
暗号的な証明が得られるわけではないため、必要に応じて版ごとの保存や差分確認、任意の署名を使えます。

Host APIとFormの仕様は、実装言語、SDK、特定のTerraform Providerから独立しています。
Hostが使うDB、記録形式、実行キューの選択も実装側が行います。
各Providerは自分が対応するFormを扱い、他の作者や業界標準のProviderと組み合わせられます。
作者によって参加条件を変えません。

共通APIへの適合と、個々のFormへの適合は分けて確認します。
機械可読な定義を使わない場合も、入力・出力・依存関係・操作の意味の検証は必要です。
共通APIの確認項目は[HTTP APIの適合確認](/spec/host-api/v2/http#conformance)に定めます。

## 6. 版と互換性

公開したAPIの意味は、そのメジャー版の中で変更しません。意味を変える場合は新しいAPI
メジャー版として定義します。サイトの構成や非規範の解説は、規範本文と分けて更新できます。
文書セットだけの別の版系列を作って契約の意味を変えることはしません。

Formは各作者の版固定URLを単位に更新します。同じResourceの通常更新で別のForm URLへ
切り替えたり、実行先を暗黙に移したりしません。共通APIは自動的な版移行を定義しません。

SDKとProviderは、それぞれ独立したソフトウェアの版で更新できます。
ソフトウェアの更新だけで、利用するAPIやFormの意味が変わることはありません。
